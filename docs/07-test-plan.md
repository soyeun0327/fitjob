## 1. 목적과 원칙

이 프로젝트의 테스트는 "코드가 맞는가"에서 끝나지 않고 **인프라가 설계대로 동작하는가**와 **장애가 나도 설계대로 버티는가**까지 검증한다.

1. **하드 조건 정확성이 최우선이다.** 신입에게 경력 전용 공고를 보여주는 것은 서비스가 해결하려는 문제 그 자체이므로, 조건 위반은 0건을 목표로 자동 측정한다.
2. **외부 데이터는 믿지 않는다.** 외부 API 응답은 계약 테스트와 품질 규칙으로 검사한 뒤 적재한다.
3. **설정이 아니라 동작을 증명한다.** Auto Scaling은 부하를 걸어 실제로 늘어나는지, NAT 복구는 실제로 꺼서 몇 분 걸리는지 측정한다.
4. **결과는 숫자로 남긴다.** 포트폴리오에 쓸 수 있도록 측정값과 날짜를 기록한다.

### 5.2 지표

| 지표 | 정의 | 목표 | 자동화 |
|---|---|---|---|
| 조건 위반률 | 결과 공고 중 RDS 기준 하드 조건(경력, 지역, 직무, 고용형태, 마감)을 어긴 비율. 판정은 [API 명세 5.2](04-api-spec.md#52-조건--필터-변환)의 변환 규칙을 따른다(배열은 하나라도 겹치면 일치, `전국`·`IT_GENERAL` 자동 포함, 연차를 말했는데 연차 미상이면 위반) | **0%** | 자동, 전체 모드 (공고 상세 API로 RDS 값 확인) |
| 조건 추출 정확도 | 필드별 기대값 일치 비율 | 90% 이상 | 자동, 두 모드 모두 |
| 거절 정확도 | 무관·인젝션 질의를 `REFUSED`로 처리한 비율 | 100% | 자동, 두 모드 모두 |
| 근거 이탈 | 답변에 결과 공고에 없는 회사명·숫자가 등장한 건수 | 0건 | 자동, 전체 모드 (문자열 대조) |
| 관련성 Precision@5 | 상위 5건 중 사람이 "적합"으로 표시한 비율 (20개 질의) | 0.7 이상 | 월 1회 수동 라벨링 |
| 응답 시간 | 채팅 p95 | 6초 이하 | 자동, 전체 모드 |

- 공고 데이터는 매일 바뀌므로 자동 지표는 "규칙 기반으로 판정할 수 있는 것"만 쓴다. 관련성은 월 1회 스냅샷으로 따로 잰다.
- 1회 실행 비용은 LLM 호출 약 100회 수준으로 무시할 만하다.
- 피드백(`DOWN`)이 달린 질의는 평가셋 후보로 옮긴다.

### 5.3 실행 방식

RDS는 프라이빗 서브넷에 있어 GitHub 러너가 직접 조회할 수 없다. 그래서 평가는 DB에 접속하지 않고 두 가지 모드로 나눠 돈다.

| 모드 | 언제 | 무엇을 호출하나 | 재는 지표 | AWS 권한 |
|---|---|---|---|---|
| 프롬프트 모드 | 프롬프트 변경 PR | 러너에서 PR의 조건 추출 프롬프트로 Bedrock을 직접 호출 | 조건 추출 정확도, 거절 정확도 | `fitjob-gha-eval` (`bedrock:InvokeModel`만) |
| 전체 모드 | 운영 단계 매일 08:00 KST, 수동 실행 | 배포된 `https://app.<도메인>`의 공개 API | 5.2의 자동 지표 전부 | 없음 |

전체 모드의 검증 방법:

- **조건 위반률:** `POST /api/v1/chat` 응답의 각 `postings[].id`로 `GET /api/v1/postings/{id}`를 호출한다. 상세 응답에는 RDS 값(경력 구분·연차, 지역, 직무, 고용형태, 학력, 마감, 상태)이 그대로 담겨 있으므로, 이를 케이스의 `expected_filters`와 대조한다.
- **조건 추출 정확도:** 응답의 `applied_filters`를 `expected_filters`와 비교한다.
- **근거 이탈:** `reply`와 각 `reason`에 결과 공고 상세에 없는 회사명·숫자가 있는지 문자열로 대조한다.
- **응답 시간:** 클라이언트에서 잰 시간과 CloudWatch `ChatLatency`를 함께 본다.
- **호출 제한:** 케이스마다 새 세션을 발급한다(세션당 분당 10회 제한). 1회 실행은 채팅 약 60회라 IP당 일 100회, 서비스 일 1,000회 상한 안에 든다. 공고 상세 조회는 최대 수백 회라 IP당 분당 120회 제한에 맞춰 속도를 조절한다([API 명세 1.5](04-api-spec.md#15-호출-제한)).
- 시작할 때 `/api/health`가 200이 아니면 실패가 아니라 건너뜀으로 끝낸다.

PR에서 조건 위반률을 재지 않는 이유: 추출한 조건을 KB·RDS 필터로 바꾸는 부분은 결정적인 코드라서 단위 테스트(필터 변환 로직)로 막는다. 프롬프트가 바꿀 수 있는 것은 조건 추출이므로 PR은 그것을 막는다. 프롬프트 변경이 배포된 뒤에는 다음 전체 모드 실행에서 조건 위반까지 확인한다.

## 6. 부하 테스트

### 6.1 시나리오 (k6)

| ID | 대상 | 부하 | 목적 |
|---|---|---|---|
| L-01 | 공고 목록·상세 | 10 → 60 rps, 15분 램프 | Auto Scaling 확장 동작, DB 쿼리 병목, t3 CPU 크레딧 |
| L-02 | 채팅 (실제 Bedrock) | 0.5 → 3 rps, 5분 | 응답 시간 분해, Bedrock 쓰로틀, NAT 인스턴스 대역폭·CPU |
| L-03 | 혼합 지속 | 목록 15 rps + 채팅 0.5 rps, 30분 | 메모리 누수, DB 연결 수, 축소(scale-in) 동작 |

### 6.2 기준

| 항목 | 기준 |
|---|---|
| 목록 p95 | 500ms 이하 |
| 채팅 p95 | 6초 이하 |
| 오류율 | 1% 미만 |
| 확장 | CPU 50% 초과 후 새 인스턴스가 정상 등록되기까지 시간 측정·기록 |

### 6.3 진행 방법

- **시작 전 체크:** ASG 변수를 2/2/4(`asg_min`/`asg_desired`/`asg_max`)로 올려 `app` 스택을 apply하고, 끝나면 운영 기본값 1/1/4로 되돌린다([인프라 명세 7.2](05-infrastructure.md#72-auto-scaling-그룹)).
- 실행 위치: 개인 PC에서 k6 (CloudFront 경유, 실제 사용자 경로와 동일)
- L-02 전에 일일 채팅 상한을 임시로 올리고, 끝나면 되돌린다. 예상 비용은 수 달러 이하.
- 함께 기록할 지표: ASG 활동 시각, 인스턴스별 CPU·CPU 크레딧, ALB 응답 시간·요청 수, RDS 연결 수·CPU, NAT 인스턴스 네트워크·CPU
- 결과로 스케일링 지표(CPU vs 요청 수)와 인스턴스 타입을 재검토하고 [ADR-004](10-adr.md)에 반영한다.

## 7. 장애 훈련 (Game Day)

실제 장애가 아니라 **계획된 훈련**이다. 각 훈련은 가설을 세우고, 장애를 주입하고, 감지·복구 시간을 잰다. 결과는 [운영 문서의 보고서 양식](08-operations.md#12-장애-훈련-보고서-양식)으로 남긴다.

**시작 전 체크:** ASG를 2/2/4로 올리고, 훈련 기간이 끝나면 운영 기본값 1/1/4로 되돌린다. 감지 시간을 재야 하므로 `observability` 스택이 켜져 있어야 한다.

| ID | 시나리오 | 주입 방법 | 가설(기대 결과) | 측정 |
|---|---|---|---|---|
| GD-01a | NAT 인스턴스 장애 (1단계, 직접 구성) | NAT 인스턴스 종료 | 목록 조회 정상, 채팅은 `DEGRADED`(키워드 검색)로 응답, deep 헬스체크 알람 | 감지 시간, 수동 복구(`nat` 스택 재적용) 시간 |
| GD-01b | NAT 인스턴스 장애 (2단계, fck-nat) | NAT 인스턴스 종료 | ASG가 새 인스턴스를 띄우고 ENI 재부착, 사람 개입 없이 복구 | 자동 복구 시간 (GD-01a와 비교) |
| GD-02 | 앱 인스턴스 1대 장애 (**2대 구성에서만 의미 있음**) | 앱 인스턴스 1대 종료 | 다른 가용영역이 처리, 5xx 거의 없음, ASG가 교체 | 5xx 건수, 교체 완료 시간 |
| GD-03 | RDS 재부팅 | RDS 재부팅 | 1~2분간 503 후 **앱 재시작 없이** 자동 회복(연결 풀 재연결) | 오류 지속 시간, 회복 여부 |
| GD-04 | Bedrock 호출 불가 | 앱 역할에 Bedrock 거부 정책 임시 부착 | 채팅이 `DEGRADED`로 응답, 오류율 알람 | 대체 응답 비율, 알람 시각 |
| GD-05 | 외부 API 인증 실패 | 한 소스의 API 키를 잘못된 값으로 교체 후 파이프라인 수동 실행 | 재시도 후 그 소스만 `FAILED`, 실행은 `PARTIAL`, **대량 마감 없음**, 알림 | 마감 처리 건수(0이어야 함), 알림 수신 |
| GD-06 | 잘못된 배포 | `/api/health`가 500을 내는 이미지 배포 | 새 인스턴스가 정상 판정을 못 받아 새로고침 실패, 파이프라인이 이전 태그로 롤백, 사용자 영향 없음 | 롤백 완료 시간, 사용자 오류 건수 |
| GD-07 | DB 복구 리허설 (분기 1회) | RDS 시점 복구로 새 인스턴스 생성 | 데이터 건수 일치, 앱 전환 절차 동작 | 복구 소요 시간(RTO), 데이터 손실 범위(RPO) |

**GD-01a → GD-01b가 포트폴리오의 핵심 서사다.** 1단계에서 수동 복구 시간과 발견한 문제(예: ALB 헬스체크는 정상인데 채팅이 실패)를 기록하고, fck-nat 전환 후 같은 훈련으로 개선 폭을 숫자로 보여준다.

GD-02는 앱 서버가 1대면 "ASG가 교체하는 수 분간 중단"이 정해진 결과라 검증할 가설이 없다. 반드시 2대 구성에서 한다.

## 8. 인프라·보안 회귀 테스트

`scripts/security-smoke.sh`를 `security-smoke.yml` 워크플로가 `infra-apply` 직후와 매주 월요일 10:30 KST에 실행하고, `make up`도 마지막 단계에서 실행한다. 워크플로에서는 퍼블릭 IP·보안 그룹 확인에 읽기 전용 역할 `fitjob-gha-tf-plan`을 쓴다. **운영 단계이거나 환경이 켜져 있을 때만 실행한다.** 예약 실행은 시작할 때 `/api/health`가 200이 아니면(개발 기간에 꺼져 있음) 실패로 보고하지 않고 건너뛴다.

| 검사 | 기대 |
|---|---|
| `https://app.<도메인>/` | 200 |
| `https://app.<도메인>/api/health/deep` | 200 |
| ALB DNS 이름으로 직접 HTTPS 요청 | 연결 불가 또는 403 (CloudFront 우회 차단) |
| 앱·RDS 인스턴스의 퍼블릭 IP | 없음 |
| 보안 그룹 중 22번 포트 인바운드 | 없음 |
| S3 웹 버킷 객체 URL 직접 요청 | 403 |
| HTTP 요청 | HTTPS로 리다이렉트 |

## 9. E2E 테스트 (Playwright)

`e2e.yml` 워크플로가 `app-deploy`·`web-deploy` 성공 직후(핵심 시나리오)와 매일 10:00 KST(전체)에 실행한다. 공개 URL만 쓰므로 AWS 권한이 필요 없다. 매일 실행은 운영 단계이거나 환경이 켜져 있을 때만 한다. 8장과 같은 방식으로, 꺼져 있으면 건너뛴다.

## 10. 테스트 환경

| 환경 | 구성 | 용도 |
|---|---|---|
| 로컬 | docker compose(PostgreSQL) + API, `BEDROCK_MODE=stub` | 개발, 단위·통합 |
| CI | GitHub 러너 + PostgreSQL 서비스 컨테이너 | PR 검증, 마이그레이션 검증 |
| 운영 | 실제 AWS. 개발 기간에는 온디맨드(`make up`으로 켰을 때만), 운영 단계에는 24시간 | 스모크, E2E, RAG 평가, 부하, 장애 훈련 |

개발 기간의 AWS 환경은 온디맨드다. 인프라 작업과 통합 확인 때만 `make up`으로 켜고, 끝나면 `make down`으로 끈다([인프라 명세 12](05-infrastructure.md#12-온디맨드-운영)). 그래서 예약 실행 테스트(E2E, 보안 회귀)는 환경이 꺼져 있으면 건너뛰고, RAG 평가 예약 실행은 운영 단계에만 돈다.

비용 때문에 별도 스테이징 환경은 두지 않는다. 대신 (1) CI에서 실제 PostgreSQL로 마이그레이션을 검증하고, (2) 배포 후 스모크 테스트와 자동 롤백으로 위험을 줄인다. 장애 훈련은 사용자가 적은 시간대에 하고, 시작·종료를 기록한다.
