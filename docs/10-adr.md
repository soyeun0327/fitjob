## ADR-001 공식 API와 공공데이터만 사용한다

- 상태: 일부 대체됨 · 날짜: 2026-11-02

> **소스 목록 중 고용24는 [ADR-013](#adr-013-두-번째-수집-소스로-공공기관-채용정보-조회서비스를-쓴다)으로 대체됐다.** 고용24 OPEN API의 채용정보는 개인 신청으로 받을 수 없어서, 두 번째 소스를 공공데이터포털의 공공기관 채용정보 조회서비스로 바꿨다. 공식 API와 공공데이터만 쓴다는 원칙, 크롤링 금지, 출처·원문 링크 표시는 그대로 유효하다.

**맥락.** 여러 채용 사이트의 공고를 모아야 한다. 크롤링하면 가장 많은 데이터를 얻을 수 있지만, 국내에서는 채용 사이트 간 무단 크롤링을 부정경쟁행위로 본 판결(잡코리아 대 사람인)이 있다. 잡코리아 API는 공공기관·학교에 우선 제공되어 개인 승인 가능성이 낮다.

**결정.** 사람인 채용정보 API와 고용24 OPEN API(필요하면 지자체 공공데이터)만 쓴다. 크롤링은 하지 않는다. 모든 공고에 출처와 원문 링크를 표시한다.

**검토한 대안.**
- 웹 크롤링: 데이터는 많지만 법적 위험이 크고, 사이트 구조가 바뀌면 깨진다.
- 상용 스크래핑 서비스: 같은 법적 위험에 비용까지 든다.

**결과.**
- 장점: 법적 위험 제거, 안정적인 데이터 형식, 면접에서 설명 가능한 판단.
- 대가: 수집 범위가 승인받은 소스로 제한된다. 승인 전에는 픽스처로 개발한다.

**재검토 조건.** 다른 채용 플랫폼이 개인에게 API를 열어줄 때.

## ADR-002 벡터 저장소로 Bedrock Knowledge Base + S3 Vectors를 쓴다

- 상태: 채택 · 날짜: 2026-11-02

**맥락.** 공고 수만 건을 의미 검색해야 한다. 개인 프로젝트라 상시 과금되는 저장소는 부담이다.

**결정.** Bedrock Knowledge Base가 S3의 공고 문서를 임베딩해 S3 Vectors에 저장하고 검색한다.

**검토한 대안.**

| 대안 | 장점 | 단점 |
|---|---|---|
| OpenSearch Serverless | 기능 풍부, KB 기본 저장소 | 최소 2 OCU가 항상 켜져 월 약 $350 |
| RDS PostgreSQL + pgvector | DB 하나로 SQL 필터와 벡터 검색을 한 쿼리에 | KB의 관리형 연동 대상이 아니어서 임베딩·동기화를 직접 구현, db.t4g.micro(메모리 1GB)에 부담 |
| S3 Vectors + KB | 이 규모에서 월 $1 미만, 동기화·임베딩을 KB가 처리 | 필터 연산자·메타데이터 크기 제한, 전용 벡터 DB보다 지연이 클 수 있음 |

**결과.**
- 장점: 비용이 거의 들지 않고, 비교 과정 자체가 비용 기반 의사결정 사례가 된다.
- 대가: 메타데이터 설계를 최소화해야 하고, KB 동기화 동작에 맞춰 문서를 관리해야 한다.

**재검토 조건.** 필터 표현 한계로 조건 위반이 생기거나, 채팅 p95가 SLO를 넘길 때 pgvector를 다시 검토한다.

## ADR-003 하드 조건은 필터, 서술형 요구는 벡터 검색으로 처리한다

- 상태: 채택 · 날짜: 2026-11-02

**맥락.** 순수 벡터 유사도는 "신입"과 "경력 3년 이상"을 비슷한 글로 본다. 그래서 조건이 맞지 않는 공고가 섞이는데, 이것이 이 서비스가 풀려는 문제 그 자체다.

**결정.**
1. LLM이 채팅에서 조건을 enum이 정해진 JSON으로 추출한다.
2. 경력·지역·직무·고용형태·학력·마감은 KB 메타데이터 필터로 건다.
3. 필터로 표현되지 않는 요구만 벡터 검색어로 쓴다.
4. 결과는 RDS에서 상태와 조건을 한 번 더 확인한다.

**검토한 대안.**
- 순수 벡터 검색: 단순하지만 조건 위반이 생긴다.
- 넓게 검색한 뒤 LLM이 골라내기: 호출 비용이 크고 LLM 판단이 틀릴 수 있다.
- 순수 SQL 필터: 정확하지만 "자동화 업무가 많은 곳" 같은 서술형 요구를 처리하지 못한다.

**결과.**
- 장점: 조건 위반을 구조적으로 막고, 위반률을 자동으로 측정할 수 있다.
- 대가: LLM 호출이 늘어 응답이 느려진다. 조건 추출이 틀리면 결과도 틀리므로 평가셋으로 관리하고, 화면의 조건 칩으로 사용자가 바로잡을 수 있게 한다.

## ADR-004 채팅 API는 EC2 + ALB + Auto Scaling으로 운영한다

- 상태: 채택 · 날짜: 2026-11-02

**맥락.** 목표 직무가 클라우드 인프라다. EC2, 로드밸런서, Auto Scaling, 인증서 같은 기본 구성요소를 직접 설계·운영한 경험이 필요하다.

**결정.** FastAPI 컨테이너를 EC2(t3.micro)에서 실행하고, ALB 뒤의 Auto Scaling 그룹에 둔다. 서브넷은 가용영역 2곳이고, 용량은 변수로 둔다(운영 기본 1/1/4, 부하 테스트·장애 훈련 기간 2/2/4). 하루 한 번 도는 수집은 Lambda로 한다.

**검토한 대안.**

| 대안 | 판단 |
|---|---|
| Lambda + API Gateway | 비용은 가장 싸지만 다뤄보는 인프라 범위가 좁다 |
| ECS Fargate | OS 관리가 없어 운영이 편하다. 네트워크 설계는 비슷하다. 이후 이전 후보 |
| EKS | 클러스터 요금만 월 약 $73, 이 규모에는 과하다 |

**결과.**
- 장점: 스케일링 정책, 헬스체크, 롤링 배포, AMI·OS 패치를 직접 다룬다. "상시 트래픽은 EC2, 배치는 서버리스"라는 판단 근거를 설명할 수 있다.
- 대가: OS 패치와 AMI 관리 책임, 앱 서버 상시 비용(운영 기본 1대, 훈련 시 2대). 1대로 운영하는 동안에는 인스턴스 장애 시 ASG가 교체하는 수 분간 API가 멈춘다.

**재검토 조건.** 부하 테스트 결과로 인스턴스 타입과 스케일링 지표를 조정한다. 운영 부담이 학습 가치보다 커지면 Fargate로 옮긴다.

## ADR-005 NAT Gateway 대신 NAT 인스턴스를 쓴다

- 상태: 채택 · 날짜: 2026-11-02

**맥락.** 프라이빗 서브넷의 앱 서버와 VPC Lambda가 Bedrock·ECR·SSM 등에 나가야 한다. 서울 리전 NAT Gateway는 개당 월 약 $32에 처리 요금이 추가된다. 예산은 월 $100이다.

**결정.** 2a 퍼블릭 서브넷에 t4g.nano NAT 인스턴스 1대를 둔다.
- 1단계: Amazon Linux 2023에 IP 포워딩과 iptables로 직접 구성해 원리를 익힌다.
- 2단계: 장애 훈련(GD-01a) 후 fck-nat 고가용성 모드(1대짜리 ASG + 고정 ENI)로 바꾸고 같은 훈련(GD-01b)으로 개선 폭을 잰다.

**검토한 대안.**
- NAT Gateway 1개: 관리가 필요 없지만 비용이 4배 이상.
- 가용영역마다 NAT Gateway: 가용성은 가장 좋지만 비용이 2배 더.
- 인터페이스 엔드포인트로 NAT 제거: 필요한 엔드포인트 6종을 2개 가용영역에 두면 NAT보다 비싸다.
- 앱 서버를 퍼블릭 서브넷에: NAT가 필요 없지만 "프라이빗이 기본값" 원칙을 깬다.

**결과.**
- 장점: NAT Gateway 대비 월 $25 이상 절감, NAT 동작 원리 학습, 장애 훈련 소재.
- 대가: 단일 장애점(2a), 인스턴스 대역폭 한계, 패치 책임.
- 완화: NAT 장애 시 채팅은 키워드 검색으로 대체 응답하고 목록은 정상 동작한다. 외부 API 수집 Lambda는 VPC 밖에 둬서 NAT와 무관하다.

**재검토 조건.** NAT 인스턴스의 CPU·네트워크가 한계에 닿거나, 가용성 요구가 올라갈 때.

## ADR-006 DB는 RDS PostgreSQL Single-AZ로 시작한다

- 상태: 채택 · 날짜: 2026-11-02

**맥락.** 공고 목록은 필터·정렬·페이지·집계가 많고, 중복·마감 처리에 정합성이 중요하다.

**결정.** RDS PostgreSQL db.t4g.micro, Single-AZ(2a), 자동 백업 7일과 시점 복구.

**검토한 대안.**
- DynamoDB: 서버리스라 거의 무료지만 다중 조건 필터·정렬·집계가 불리하고, 네트워크 설계 학습 요소가 줄어든다.
- RDS Multi-AZ: 가용영역 장애에 자동 대응하지만 비용이 2배.
- Aurora Serverless: 최소 용량 비용이 이 규모에서 더 크다.

**결과.**
- 장점: 제약조건으로 데이터 정합성을 DB 수준에서 보장, SQL로 필터·집계, DB 서브넷 설계 경험.
- 대가: 월 약 $21. 2a 장애 시 시점 복구로 수동 전환(RTO 2시간 목표).
- RDS를 NAT와 같은 2a에 둬서 "2c 장애는 무영향, 2a 장애는 전체 영향"으로 단순화했다.
- 개발 기간에는 변수 `rds_ephemeral = true`로 삭제 보호와 최종 스냅샷을 끄고 RDS도 온디맨드로 켜고 끌 수 있다. 공고는 S3 `staging/`에서 replay로 다시 채운다([ADR-011](#adr-011-개발-기간에는-비싼-리소스를-온디맨드로-운영한다)).

**재검토 조건.** 가용성 목표를 올릴 때 Multi-AZ로 전환한다.

## ADR-007 처음부터 Terraform으로 관리하고 스택을 나눈다

- 상태: 일부 대체됨 · 날짜: 2026-11-02

> **진행 방식은 [ADR-012](#adr-012-인프라를-콘솔로-먼저-만들고-terraform으로-가져온다)로 대체됐다.** "처음부터 Terraform으로 만들고, 콘솔로는 만들어 보고 지운다"는 방식 대신 "콘솔로 먼저 만들고 Terraform으로 가져온다". 모든 리소스를 Terraform으로 관리한다는 목표, 스택 9개 구성, S3 state와 자체 잠금은 그대로 유효하다.

**맥락.** Terraform 경험이 없다. 콘솔로 먼저 만들고 나중에 코드로 옮길지 고민했다.

**결정.** 처음부터 Terraform으로 만든다. 각 구성요소는 콘솔로 한 번 만들어 보고 지운 뒤 코드로 다시 만든다. 스택은 상시 스택 bootstrap, network, storage, edge, pipeline과 온디맨드 스택 nat, database, app, observability, 모두 9개로 나눈다([인프라 명세 10.2](05-infrastructure.md#102-스택-구성과-적용-순서)). state는 S3에 두고 S3 자체 잠금(`use_lockfile`)을 쓴다.

**검토한 대안.**
- 콘솔로 만들고 나중에 import: 리소스 수십 개를 하나씩 가져와야 해서 결국 하지 않게 되는 경우가 많다.
- CloudFormation·CDK: AWS 전용. 채용 공고에서는 Terraform을 더 많이 요구한다.
- 단일 스택: 단순하지만 앱 변경 plan이 DB까지 건드리고, 일부만 destroy하기 어렵다.

**결과.**
- 장점: 재현성, 온디맨드 스택만 켜고 꺼서 비용 절감([ADR-011](#adr-011-개발-기간에는-비싼-리소스를-온디맨드로-운영한다)), 커밋 이력이 인프라 변천사가 된다.
- 대가: 초기 진행이 느리다.

## ADR-008 MVP에서는 로그인을 넣지 않는다

- 상태: 채택 · 날짜: 2026-11-02

**결정.** 서버가 발급하는 익명 세션 ID로 대화를 구분하고, 호출 제한은 세션과 IP 해시 기준으로 한다.

**검토한 대안.** Cognito 로그인: 관심 공고 저장, 알림이 가능해지지만 인증 흐름과 API가 늘어난다.

**결과.**
- 장점: 범위가 줄어 인프라에 집중, 수집하는 개인정보 최소화.
- 대가: 관심 공고·알림 불가, IP 기준 제한이라 남용 방지가 약하다(일일 전체 상한으로 비용은 보호).

**재검토 조건.** 운영 중 사용자 요구가 확인될 때.

## ADR-009 CloudFront 단일 도메인으로 웹과 API를 제공하고 ALB를 보호한다

- 상태: 채택 · 날짜: 2026-11-02

**맥락.** 웹(S3)과 API(ALB)를 각각 다른 도메인으로 노출하면 CORS 설정이 필요하고, ALB가 인터넷에 그대로 열린다.

**결정.** CloudFront가 `/api/*`는 ALB로, 나머지는 S3로 보낸다. ALB는 (1) 보안 그룹에서 CloudFront 오리진용 접두사 목록만 허용하고, (2) CloudFront가 붙이는 비밀 헤더가 맞을 때만 요청을 전달한다.

**검토한 대안.**
- `api.<도메인>`으로 ALB 직접 노출: 단순하지만 공격면이 넓고 CORS가 필요하다.
- **CloudFront VPC 오리진 + 내부(internal) ALB:** ALB를 프라이빗 서브넷에 두고 CloudFront만 접근하게 하는 방식. 퍼블릭 IP 비용과 비밀 헤더 관리가 사라진다. 참고 자료가 상대적으로 적어 1차로는 공개 ALB 방식을 쓰고, Phase 5 보안 강화 때 전환을 검토한다.

**결과.**
- 장점: 진입점이 하나, ALB 우회 접근 차단, CORS 불필요.
- 대가: 비밀 헤더 교체 절차를 관리해야 한다([인프라 명세 4](05-infrastructure.md#4-엣지-보안-cloudfront--alb)).

## ADR-010 헬스체크를 얕은 것과 깊은 것으로 나눈다

- 상태: 채택 · 날짜: 2026-11-02

**맥락.** ALB 헬스체크가 DB·외부 호출까지 확인하면, NAT나 DB가 멈췄을 때 모든 인스턴스가 비정상으로 판정된다. 그러면 ASG가 멀쩡한 인스턴스를 계속 교체하고, 살릴 수 있었던 목록 기능까지 멈춘다. 반대로 얕은 체크만 있으면 NAT 장애가 아무 데도 드러나지 않는다.

**결정.**
- `/api/health`: 프로세스 생존만 확인. ALB 대상 그룹이 쓴다.
- `/api/health/deep`: DB 연결과 외부 호출 경로(STS 호출)를 확인. Route 53 헬스체크와 알람이 쓴다. 30초 캐시.

**결과.**
- 장점: 부분 장애 때 가능한 기능은 계속 제공하면서 장애는 감지한다.
- 대가: 엔드포인트 2개를 관리해야 하고, deep 엔드포인트가 공개 경로에 있으므로 캐시와 호출 제한이 필요하다.

## ADR-011 개발 기간에는 비싼 리소스를 온디맨드로 운영한다

- 상태: 채택 · 날짜: 2026-11-02

**맥락.** 24시간 켜두면 월 약 $94~103이다. 그중 약 $90은 사용량과 관계없이 시간당 과금되는 고정비다(ALB ~$20, 앱 EC2 2대 ~$21, RDS ~$21, 퍼블릭 IPv4 3개 ~$11, NAT ~$4, 앱 서버 EBS ~$3, CloudWatch ~$5 등). 개발 기간에는 혼자 하루 몇 시간만 작업하므로 리소스가 대부분의 시간 놀고 있다. 켜져 있는 동안의 비용은 시간당 약 $0.11(RDS 포함), RDS를 빼면 약 $0.08이다.

**결정.**

1. **스택을 상시 5개와 온디맨드 4개로 나눈다.** 상시 스택만 켜둔 대기 비용은 월 약 $5다.
   - 상시(무료·저렴하거나 다시 만들기 번거로운 것): `bootstrap`(state 버킷, OIDC, Budgets, 공용 SNS 토픽), `network`(VPC, 서브넷, 라우팅 테이블, 보안 그룹 전부), `storage`(S3, S3 Vectors, KB, ECR, Secrets Manager), `edge`(CloudFront, ACM, Route 53 호스팅 영역), `pipeline`(Lambda, Step Functions, Scheduler)
   - 온디맨드(작업할 때만 켬): `nat`, `database`, `app`(`origin.<도메인>` 레코드 포함), `observability`(운영 단계에만)
   - Budgets는 끌 때 비용 알림까지 사라지지 않게 `bootstrap`에, 보안 그룹은 서로 참조해서 destroy 의존성 오류가 나지 않게 `network`에, 시크릿은 삭제 후 복구 대기 기간에 같은 이름으로 다시 못 만들어서 `storage`에 둔다.
   - 상시 스택은 온디맨드 스택을 참조하지 않는다. DB 주소처럼 필요한 값은 SSM 파라미터로 넘기고 실행할 때 읽는다.
2. **Makefile로 켜고 끈다.** `make up`(`nat` → `database` → `app`, 약 15~20분), `make down`(역순, 약 10분), RDS를 빼고 켜고 끄는 `make up-app`·`make down-app`. `make up` 마지막 단계에서 `alembic upgrade head`를 실행하고, RDS를 새로 만들었으면 replay로 공고를 다시 채운다.
3. **끄는 걸 잊는 사고를 막는다.** GitHub Actions `nightly-down`이 매일 03:00 KST에 `make down`을 실행한다(수동 실행 가능, 전용 역할 `fitjob-gha-env-down`). 운영 단계에는 저장소 변수 `NIGHTLY_DOWN = off`로 멈춘다.
4. **RDS는 Phase 2(데이터 파이프라인) 동안 계속 켜둔다**(월 약 $21, `deletion_protection = true`). 마감 처리, 수집 건수 7일 평균 비교, 중복 병합처럼 여러 날의 DB 상태가 이어져야 확인되는 로직을 만드는 단계라서다. 파이프라인이 안정된 Phase 3부터는 `rds_ephemeral = true`로 삭제 보호와 최종 스냅샷을 끄고 up/down에 포함해도 된다. `rds_ephemeral = false`인 동안 `make down`은 `database`를 건너뛴다. 공고는 S3 `staging/`에서 replay로 다시 채울 수 있어 RDS를 지워도 잃을 게 거의 없고, 채팅 기록은 개발 중 데이터라 보존하지 않는다.
5. **개발 기간에도 수집은 매일 돌리되 S3까지만 한다.** 변수 `schedule_mode`로 05:00 예약 실행의 모드를 정한다. 개발 중에는 `collect_only`로 수집·정규화만 해서 S3에 쌓는다(VPC 밖 Lambda라 NAT·RDS가 필요 없다). 운영 단계에는 `full`로 적재·KB 동기화까지 한다. 개발 중 적재는 작업할 때 쌓인 날짜를 순서대로 replay해서 한다. 이렇게 하면 replay할 최신 데이터가 늘 있다.
6. **앱 개발은 로컬에서 한다**(docker compose + `BEDROCK_MODE=stub`). AWS는 인프라 작업과 통합 확인 때만 켠다.
7. **운영 단계(W12~14)에는 3~4주 동안 24시간 운영**해 SLO·운영 지표를 쌓는다. 앱 서버는 기본 1/1/4, 부하 테스트·장애 훈련 기간에만 2/2/4. 월 약 $82~91이고, CloudFront VPC 오리진으로 ALB를 내부용으로 바꾸면 약 $75~84다(전환은 Phase 5 검토 항목). 운영이 끝나면 `make down`으로 내리고, 면접·데모 때 `make up`으로 약 20분 안에 다시 띄운다.

단계별 예상 비용은 [아키텍처 11.2](02-architecture.md#112-단계별-예상-비용), 운영 절차는 [인프라 명세 12](05-infrastructure.md#12-온디맨드-운영) 참고.

**검토한 대안.**

| 대안 | 판단 |
|---|---|
| 24시간 상시 운영 | 단순하지만 월 $94~103으로 예산 상한에 붙는다. 14주 총액 약 $195~210 |
| 인스턴스 정지·ASG 0으로 축소 | ALB·퍼블릭 IP·RDS 스토리지 비용이 그대로 남고, RDS는 정지해도 7일 뒤 자동으로 다시 켜진다 |
| 서버리스로 전환 (Lambda·API Gateway·DynamoDB, NAT 없음) | 월 $5~15지만 목표 경험(EC2·ALB·Auto Scaling·RDS 운영)을 잃는다([ADR-004](#adr-004-채팅-api는-ec2--alb--auto-scaling으로-운영한다)) |

**결과.**
- 장점: 개발 기간 월 비용이 약 $95에서 $15~35로 줄어 14주 총액이 약 $90~135가 된다. "명령 한 번으로 약 20분 안에 전체 인프라 재현"을 반복해서 증명하게 되고, 이것이 포트폴리오 포인트가 된다.
- 대가: 켤 때마다 15~20분을 기다린다. 상시·온디맨드 경계, 스택 간 참조 방향, 시크릿·보안 그룹 위치를 신경 써야 해서 스택 설계가 복잡해진다. 끄는 걸 잊을 위험이 있다(nightly-down과 Budgets 알림으로 완화). 개발 기간에는 대시보드·알람이 없고 SLO를 재지 않는다.

**재검토 조건.** 상시 사용자가 생기면 24시간 운영으로 전환한다.

## ADR-012 인프라를 콘솔로 먼저 만들고 Terraform으로 가져온다

- 상태: 채택 · 날짜: 2026-11-02 · [ADR-007](#adr-007-처음부터-terraform으로-관리하고-스택을-나눈다)의 진행 방식을 대체

**맥락.** AWS와 Terraform 모두 처음이다. ADR-007은 처음부터 Terraform으로 만들고, 콘솔로는 한 번 만들어 보고 지운 뒤 코드로 새로 쓰는 방식이었다. 이렇게 하면 콘솔에서 고른 설정이 어떤 Terraform 인자에 해당하는지, 콘솔이 자동으로 만드는 리소스가 무엇인지를 직접 맞춰 볼 기회가 없다. 또 Terraform 1.5부터 생긴 `import` 블록과 설정 자동 생성(`-generate-config-out`) 덕분에, ADR-007이 걱정한 "리소스를 하나씩 가져오다 결국 안 하게 되는" 부담이 줄었다.

**결정.** 스택마다 아래 순서를 반복한다. 상세 절차는 [인프라 명세 13](05-infrastructure.md#13-콘솔-구축-후-terraform으로-가져오기).

1. 콘솔(AWS 관리 콘솔 웹 화면)로 만든다. 이름 규칙과 태그(`ManagedBy=console`)를 처음부터 붙이고 설정을 기록한다.
2. Terraform 코드를 쓰고 `import` 블록으로 state에 가져온다.
3. `terraform plan`이 "No changes"가 될 때까지 코드를 맞춘다.
4. 지워도 되는 스택은 destroy 후 apply로 코드만으로 다시 만들어지는지 확인한다(온디맨드 스택은 `make down`·`make up`).
5. 그 뒤로는 Terraform으로만 바꾼다(콘솔 수동 변경 금지).

예외: Lambda 코드는 처음부터 저장소에서 패키징하고, 시크릿 값은 import하지 않는다. 일정은 2주 늘려 14주로 한다(Phase 1·3 각 +1주).

**검토한 대안.**

| 대안 | 판단 |
|---|---|
| 처음부터 Terraform (ADR-007 원래 방식) | 빠르지만 콘솔 설정과 코드의 대응, 자동 생성 리소스를 덜 배운다 |
| 콘솔로 만들고 지운 뒤 메모를 보고 코드 새로 작성 | 콘솔 결과와 코드의 차이를 `plan`으로 비교할 수 없어 빠뜨린 설정을 찾기 어렵다 |
| 콘솔로만 운영 | 재현할 수 없고 온디맨드 운영(ADR-011)이 불가능하다 |

**결과.**
- 장점: 서비스 설정을 화면으로 익힌 뒤 코드와 1:1로 맞춰 보며 `plan` 차이를 읽는 능력이 생긴다. "기존 인프라를 코드로 가져와 재현성까지 검증"이라는 실무형 경험이 포트폴리오가 된다.
- 대가: 일정이 2주 늘어난다. 콘솔로 만든 리소스는 가져오기 전에는 state에 없어서 `make down`·nightly-down이 지우지 못한다(당일 import 또는 직접 삭제, `ManagedBy=console` 태그로 완화). 콘솔 마법사가 자동으로 만든 리소스를 정리하는 수고가 든다.

**재검토 조건.** import가 반복해서 막혀 일정이 1주 이상 더 밀리면, 남은 스택은 처음부터 Terraform으로 만든다.

## ADR-013 두 번째 수집 소스로 공공기관 채용정보 조회서비스를 쓴다

- 상태: 채택 · 날짜: 2026-11-03 · [ADR-001](#adr-001-공식-api와-공공데이터만-사용한다)의 소스 목록 중 고용24를 대체

**맥락.** ADR-001은 사람인 채용정보 API와 고용24 OPEN API를 쓰기로 했다. 그런데 고용24에 신청해 보니 개인 신청으로는 채용정보를 받을 수 없었다(2026-11-03). 대신 찾은 공공데이터포털의 `국가데이터처_채용공고` CSV는 국가데이터처가 통계 조사원을 뽑은 자체 공고 1,338건이었다. 갱신 주기는 "수시(1회성)", 마지막 수정은 2025-08-06이고, 경력·지역·직무·학력·마감일 컬럼이 없다.

**결정.** 두 번째 소스로 공공데이터포털의 `재정경제부_공공기관 채용정보 조회서비스`를 쓴다. 공공기관 채용 사이트 잡알리오의 공시 데이터다. 소스 코드는 `alio`, 표시 이름은 `공공데이터포털`이다. 처음에는 표시 이름을 `잡알리오`로 정했으나 같은 날 바꿨다. 잡알리오는 데이터를 공시하는 사이트이고, API는 공공데이터포털이 제공하기 때문이다.

**검토한 대안.**

| 대안 | 판단 |
|---|---|
| 고용24 OPEN API | 개인 신청으로는 채용정보를 받을 수 없다 |
| 국가데이터처_채용공고 CSV | 통계 조사원 자체 공고만 있고 1회성이다. 하드 조건 필드가 없다 |
| 공공기관 채용정보 조회서비스 | 실시간 갱신. 채용구분·근무지역·고용유형·학력·NCS 직무·공고 종료일·출처 URL이 목록 조회 응답에 있다. 개발 단계는 자동 승인 |
| 지자체 일자리 공공데이터 | 지역이 한정된다. 소스를 더 늘릴 때의 후보 |

**결과.**
- 장점: 하드 조건 대부분이 코드 필드로 와서 필터에 바로 쓸 수 있다. 목록 조회만으로 필요한 필드가 다 와서 호출 수가 적다. 이용허락범위가 "제한 없음"이다. 사람인에도 올라오는 공공기관 공고가 있어 중복 병합(FR-C05)을 실제 데이터로 확인할 수 있다.
- 대가: 공공기관 공고만 있어 민간 기업 공고는 사람인에 기댄다. 경력 연차 필드가 없고, NCS 분류는 통합 직무 분류보다 거칠어 매핑표가 필요하다. 연차는 미상으로 두고, IT 공고는 `IT_GENERAL`로 받는 것으로 정했다([DB 스키마 7.1](03-db-schema.md#71-공공데이터포털-코드-매핑)). 개발 계정 트래픽은 1,000회이고, 운영 계정은 심의 승인이다.

**재검토 조건.** 사람인 승인이 거절되면 이 소스가 첫 번째 소스가 된다([로드맵 R-01](09-roadmap.md#6-위험-관리)). 고용24가 개인에게 채용정보를 열면 다시 검토한다.
