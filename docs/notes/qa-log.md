### Q2. 버킷을 만들 때 태그는 왜 붙여야 해?

태그는 리소스에 붙이는 `키=값` 이름표다. AWS가 동작하는 데는 필요 없지만, 이 프로젝트에서는 다음에 쓴다.

| 태그 | 쓰는 곳 | 없으면 생기는 일 |
|---|---|---|
| `Project=fitjob` | 비용 추적. 결제 콘솔에서 비용 할당 태그로 켜면 Cost Explorer에서 FitJob 비용만 따로 본다 | 계정의 다른 비용과 섞인다. 매월 예상 대비 실제 비용 기록과 Phase 7 비용 리포트를 만들 수 없다 |
| `ManagedBy=console` | 정리 누락 방지. 콘솔로 만들고 아직 Terraform으로 가져오지 않은 리소스를 이 태그로 찾는다 | Terraform이 모르는 리소스는 `make down`이 지우지 못해 계속 과금된다. Phase 1 완료 기준에 "`ManagedBy=console` 남은 리소스 0개"가 있다 |
| `Stack=nat` 등 | 소속 확인. 어느 스택 리소스인지, 꺼지지 않은 온디맨드 리소스가 있는지 찾는다([운영 RB-08](../08-operations.md#rb-08-make-updown-실패--꺼지지-않은-리소스)) | 리소스를 하나씩 열어 봐야 한다 |
| `Env=prod` | 환경 구분 | 지금은 환경이 하나라 영향이 거의 없다 |

**왜 만들 때 붙이나.**
- 비용 태그는 소급되지 않는다. 붙이기 전에 쓴 비용은 태그 없이 집계된다.
- 나중에 붙이려면 잊기 쉽고, 잊은 리소스는 검색에서 빠져 과금이 이어질 수 있다.
- Terraform으로 가져온 뒤에는 코드의 `default_tags`가 자동으로 붙여 준다. 손으로 붙이는 건 콘솔 단계에서만이다([인프라 명세 13.2](../05-infrastructure.md#132-콘솔-단계-규칙)).

**연습 버킷은?** 빈 버킷이고 곧 지우므로 영향은 작다. 그래도 비용 할당 태그 활성화(Phase 0 할 일)에는 `Project` 태그가 붙은 리소스가 있어야 한다. Phase 1부터는 콘솔로 만드는 모든 리소스에 태그를 붙여야 하니 습관을 미리 들이는 의미도 있다.

### Q3. Stack은 정확히 무엇을 뜻해? 해야 할 일을 스택에 쌓아 둔 것으로 보면 돼?

아니다. 할 일은 로드맵의 Phase와 작업 행이 맡는다. 이 프로젝트에서 **스택은 한 번에 같이 만들고 같이 지우는 AWS 리소스 묶음**이다.

| 구성 | 예: `network` 스택 |
|---|---|
| 코드 폴더 하나 | `infra/stacks/network/` |
| state 파일 하나 (Terraform이 자기가 만든 리소스를 기록하는 장부) | `stacks/network/terraform.tfstate` |
| 담긴 리소스 | VPC, 서브넷 6개, 라우팅 테이블, 보안 그룹 등 |
| 명령의 범위 | 이 폴더에서 `plan`·`apply`·`destroy`를 하면 이 묶음만 바뀐다 |

**"쌓는다"는 느낌은 맞다. 다만 쌓는 건 인프라 층이다.** 아래 층이 있어야 위 층을 올릴 수 있다.

```
 8  observability   ← 알람·대시보드 (운영 때만)
 7  app             ← 서버·로드밸런서
 6  database        ← RDS
 5  nat             ← 외부 통신 장치
 4  pipeline        ← 수집 Lambda
 3  edge            ← CloudFront·인증서
 2  storage         ← S3·시크릿·KB
 1  network         ← VPC·서브넷 (모든 것의 바닥)
 0  bootstrap       ← state 버킷·예산 알림
```

- 만들 때는 아래에서 위로(0 → 8), 지울 때는 위에서 아래로.
- 예: `app`은 `network`의 서브넷 위에 서버를 올리므로 `network`가 먼저 있어야 한다.

**왜 9개로 나눴나.** 가장 큰 이유는 비용이다.

| 구분 | 스택 | 개발 기간 운영 |
|---|---|---|
| 상시 (5개) | bootstrap, network, storage, edge, pipeline | 켜 둬도 월 약 $5라 항상 둔다 |
| 온디맨드 (4개) | nat, database, app, observability | 시간당 요금이 붙어 작업할 때만 `make up`으로 켜고 `make down`으로 지운다 |

한 묶음이면 비싼 것만 골라 끌 수 없다. 나눠 두면 위쪽 층만 걷어냈다가 다시 올릴 수 있다. 앱을 고칠 때 `plan`이 DB를 건드리지 않는 장점도 있다. 자세한 구성은 [인프라 명세 10.2](../05-infrastructure.md#102-스택-구성과-적용-순서).

**태그 `Stack`과의 관계.** 리소스가 9개 묶음 중 어디 소속인지 적는 이름표다. `make down` 뒤에 `Stack=app` 리소스가 남아 있으면 끄다가 실패한 것이다. 연습 버킷의 `Stack=practice`는 9개 어디에도 속하지 않는 임시 연습용 값이다.

### Q4. 지금 Terraform으로 작성된 거야? 확인하려면 어떻게 해?

코드는 Terraform 언어(HCL)로 작성돼 있다. 하지만 `apply` 전이라 장부(state)가 비어 있어서, Terraform은 아직 버킷을 자기 것으로 보지 않는다. 코드·장부·실물의 관계와 확인 명령(`terraform plan`, `terraform state list`)은 [Terraform 기초 학습 노트 1.1](terraform-basics.md#11-세-가지를-비교한다)과 [2장](terraform-basics.md#2-기본-명령)에 있다.

[Terraform 기초 학습 노트](terraform-basics.md)에 정리했다. Claude가 코드를 만들고 `apply`까지 하면 연습이 되지 않으므로, 명령은 사용자가 직접 실행한다([학습 노트 8장](terraform-basics.md#8-직접-해-보기)).

조직 정책(SCP)은 없고(조직 미가입), 사용자는 관리자 권한이며, 권한·리전 상태도 모두 정상이다. 그래서 AWS 쪽 계정 제한으로 보고 AWS Support("Account and billing" 유형)에 문의했다(케이스 179550130900646). 문의 전 AWS AI 자동 점검은 결제 수단 오류·확인 필요 가능성을 살펴봤지만 추천을 내지 못했다. 예시 요청 ID는 `33efbe74-557b-4891-8a97-44616a973d40`(06:00 UTC)이다.

같은 날 저녁, 결제 카드가 만료돼 있던 것을 찾아 새 카드로 바꿨다. 카드 문제가 계정 제한의 원인일 수 있어 양식과 계약을 처음부터 다시 했지만 그래도 거부됐다. 양식·계약·권한은 모두 정상이므로, 남은 것은 AWS 내부의 계정 단위 허용이고 이것은 Support만 풀 수 있다. 케이스에 카드 교체 사실을 회신으로 알리기로 했다.

양식을 CLI로 다시 낼 때 주의할 점이 있다. `get-use-case-for-model-access`가 돌려주는 `formData`는 base64가 두 겹이다. 그대로 `put-use-case-for-model-access --form-data`에 넣으면 `Invalid form data`가 나고, base64를 한 번 풀어서 넣어야 받아준다.

앱 개발은 `BEDROCK_MODE=stub`으로 하므로 당장 막히지 않는다. 실제 호출은 Phase 3(2027-01-04~) 전까지만 되면 된다. Support로도 안 되면 Amazon 모델(Nova 등)로 바꾸는 방안을 따로 정한다.

### Q9. S3 Vectors 필터 실측(Q-05)은 무엇을 하는 거야?

채팅 검색의 "조건 거르기"가 우리가 고른 저장소(S3 Vectors)에서 AWS 문서대로 동작하는지, 가짜 공고로 직접 돌려 보는 시험이다.

검색은 두 단계다. 먼저 뜻이 비슷한 공고를 찾고(벡터 검색), 다음에 공고에 붙은 꼬리표(메타데이터)로 지역·경력·고용형태가 안 맞는 공고를 뺀다(필터). 설계 원칙상 두 번째 단계는 반드시 필터로 한다([ADR-003](../10-adr.md)). 그런데 꼬리표 대부분이 `regions = ["서울", "경기"]` 같은 목록이고, 목록 필터(`listContains`)는 KB 문서에 "OpenSearch Serverless에서 가장 잘 지원된다"고만 적혀 있다. OpenSearch Serverless는 월 약 $350이라 S3 Vectors를 골랐으니, S3 Vectors에서 되는지 직접 봐야 한다.

| # | 확인할 것 | 안 되면 |
|---|---|---|
| 1 | 목록 필터(`listContains`, `in`)가 되나 | 지역·직무·고용형태 필터 방식을 바꾼다 |
| 2 | `andAll`·`orAll`에 조건 6개 이상, 2단계 중첩이 되나(문서상 5개, 1단계) | 필터를 줄이고 일부를 RDS 재확인으로 넘긴다 |
| 3 | 빈 목록 `[]` 꼬리표를 받아주나, 목록 필터에서 빠지나 | 키를 빼거나 표시값을 넣는다(안 받아주면 KB 동기화가 실패한다) |
| 4 | 키가 없는 문서가 필터에서 빠지나 | 참고용(연차 미상은 표시값 99로 이미 해결) |

방법은 CLI 스크립트 하나로 임시 리소스(문서용 S3 버킷, 벡터 버킷·인덱스, KB, KB용 IAM 역할)를 만들고, 가짜 공고 10개를 넣어 필터마다 기대한 공고만 나오는지 비교한 뒤 같은 날 전부 지우는 것이다. 비용은 1센트 미만이다. Titan 임베딩만 쓰므로 Haiku 문제와 상관없이 할 수 있다. 결과는 Q-05와 [API 명세 5.2](../04-api-spec.md#52-조건--필터-변환), [DB 스키마 9](../03-db-schema.md#9-kb-문서-형식)에 반영한다. AWS에 리소스를 만드는 일이라 사용자가 요청할 때 한다.

### Q10. AWS Support에서 온 이 글이 답변 맞아?

아니다. 붙여 넣은 글은 케이스를 만들 때 보낸 문의 원문이었다. 케이스가 접수되면 원문이 담긴 확인 메일이 온다.

### Q12. Squash and merge가 뭐였지?

PR에 든 커밋 여러 개를 **하나로 합쳐** `main`에 넣는 병합 방식이다(squash는 "눌러 찌그러뜨린다"는 뜻). PR #2를 예로 들면, 브랜치에 커밋이 2개(`950965b` 문서 반영, `c3b3755` 해시 반영) 있었다.

| 방식 | `main`에 남는 것 | 특징 |
|---|---|---|
| Create a merge commit (PR #1) | 브랜치 커밋 2개 + "Merge pull request" 커밋 | 과정이 모두 남지만 `main`이 지저분해진다 |
| **Squash and merge** (저장소 규칙, PR #2·#3) | 새 커밋 1개 (PR #2는 `d7e2baf`) | PR 1개 = 커밋 1개라 `main`을 읽기 쉽다. 자세한 과정은 PR 페이지에 남는다 |
| Rebase and merge | 브랜치 커밋 2개가 새 해시로 다시 쌓임 | 병합 커밋은 없지만 커밋 수는 그대로다 |

**스쿼시하면 생기는 일**

| 일 | 대응 |
|---|---|
| 브랜치에서 만든 커밋의 해시가 `main`에 남지 않는다. 로드맵 7장에 적은 `950965b`가 `main`에 없는 해시가 됐다 | 완료 기록에 커밋 해시 대신 **PR 번호**를 적기로 했다(답: `1A`, PR #3). 번호는 스쿼시해도 바뀌지 않는다 |
| PR 제목이 그대로 `main`의 커밋 제목이 된다. PR #2는 제목을 고치지 않아 브랜치 이름에서 나온 `Docs/phase0 q03 q05 (#2)`가 들어갔다 | PR을 만들 때 제목 칸을 Conventional Commits 형식(`docs: ...`)으로 먼저 바꾼다. 이미 들어간 제목은 `main` 강제 푸시가 필요해 그대로 둔다 |
| Git은 스쿼시된 브랜치를 "병합 안 됨"으로 본다 | 로컬 브랜치는 `main`과 내용이 같은 것을 확인한 뒤 `git branch -D`로 지운다 |

### Q13. 비용 할당 태그 `Project`를 활성화했는데, 결제 화면에서 어떻게 달라져?

**청구서(Bills) 화면은 그대로다.** 청구서는 서비스별로만 나온다. 달라지는 곳은 비용을 나눠 보는 화면이다.

| 화면 | 활성화 전 | 활성화 후 |
|---|---|---|
| Cost Explorer | 서비스·리전·계정 같은 기준으로만 묶을 수 있다 | 그룹 기준(Group by)에 **태그 → `Project`**가 생긴다. 비용이 `fitjob`과 "`Project` 태그 없음"으로 나뉜다. 필터로 `Project = fitjob`만 골라 볼 수도 있다 |
| Budgets | 계정 전체 비용만 본다 | 예산 필터에 태그를 걸어 "FitJob 리소스 비용만" 보는 예산을 만들 수 있다 |
| 비용 보고서(Data Exports) | 태그 열이 없다 | `Project` 태그 열이 생긴다 |

**보는 법.** 결제 및 비용 관리 → Cost Explorer → 오른쪽 보고서 설정에서 그룹화 기준(Group by)을 "태그"로 바꾸고 `Project`를 고른다.

**주의할 점**

| 항목 | 내용 |
|---|---|
| 반영 시간 | 활성화한 뒤 최대 24시간이 지나야 Cost Explorer에 나타난다. 실제로 14:43 KST에 활성화(`list-cost-allocation-tags`에서 `Active`)하고 7분 뒤 열어 보니 Cost Explorer의 태그 목록에 `Project`가 없었다. 상태는 결제 및 비용 관리 → 비용 할당 태그 화면에서 본다 |
| 과거 비용 | 기본은 활성화한 뒤의 비용부터 태그로 나뉜다. 비용 할당 태그 화면의 소급 적용(backfill)으로 최대 12개월 전까지 다시 계산하도록 요청할 수 있다 |
| 태그가 붙지 않는 비용 | 태그는 리소스에 붙는다. 그래서 리소스가 아닌 비용은 "태그 없음"으로 간다. 예: Bedrock 모델 호출(KB 임베딩, Haiku. 애플리케이션 추론 프로필을 따로 만들어 태그를 붙이면 나눌 수 있다), Cost Explorer API 요금, 세금, 도메인 등록비. 그래서 `Project = fitjob` 합계는 FitJob 전체 비용보다 작다 |
| 지금 보이는 것 | 태그가 붙은 리소스는 연습 버킷 하나이고 비용도 거의 0원이라 그래프가 비어 보인다. Phase 1에 NAT 인스턴스를 켜면 처음으로 의미 있는 숫자가 나온다 |

**이 프로젝트에서 쓰는 곳.** 로드맵의 "매월 비용 내역(단계별 예상과 실제 비교)"과 Phase 7 비용 리포트([로드맵 4장](../09-roadmap.md#4-포트폴리오-기록-체크리스트))다. 계정 전체 비용과 `Project = fitjob` 비용을 함께 적으면, 태그로 잡히지 않는 비용이 얼마인지도 보인다.

### Q14. `~/.terraformrc`에 캐시 폴더를 설정하고 `terraform init`을 했는데, 프로바이더가 캐시에 저장됐는지 어떻게 확인해?

캐시가 동작하면 프로바이더 **원본은 캐시 폴더에 한 벌만** 있고, 실습 폴더의 `.terraform` 안에는 그 원본을 가리키는 **바로가기(심볼릭 링크)**만 생긴다. 이 두 가지를 확인한다. 명령은 WSL 터미널에서 실행한다.

| # | 명령 | 캐시가 동작하면 | 확인하는 것 |
|---|---|---|---|
| 1 | `cat ~/.terraformrc` | `plugin_cache_dir = "$HOME/.terraform.d/plugin-cache"` | 설정 파일이 있고 오타가 없다 |
| 2 | `find ~/.terraform.d/plugin-cache -type f` | `.../registry.terraform.io/hashicorp/aws/6.xx.x/linux_amd64/terraform-provider-aws_v6.xx.x_x5` 한 줄 | 캐시 폴더에 프로바이더 원본이 있다. 폴더 이름이 `주소/회사/이름/버전/OS_CPU` 순서다 |
| 3 | `du -sh ~/.terraform.d/plugin-cache` | 800MB쯤(6.74.0은 775MB) | 원본 크기가 캐시 쪽에 잡힌다 |
| 4 | 실습 폴더에서 `ls -l .terraform/providers/registry.terraform.io/hashicorp/aws/*/` | `linux_amd64 -> /home/<사용자>/.terraform.d/plugin-cache/.../linux_amd64` | `->`는 바로가기라는 뜻이다. 실습 폴더는 캐시의 원본을 가리킬 뿐이다 |
| 5 | 실습 폴더에서 `du -sh .terraform` | 몇 KB | 실습 폴더에는 원본이 없다. 캐시가 없으면 여기가 800MB쯤이다 |
| 6 | `.terraform.lock.hcl`이 있는 폴더에서 `terraform init` (예: 실습 폴더의 `.terraform`만 지우고 다시) | `- Using hashicorp/aws v6.xx.x from the shared cache directory` | 가장 확실한 증거다. 내려받지 않고 캐시에서 꺼내 썼다 |

처음 `init`할 때는 캐시가 비어 있으므로 캐시를 켜도 평소처럼 `Installing hashicorp/aws ...` → `Installed ... (signed by HashiCorp)`가 나온다. 그래서 첫 폴더는 2~5번으로 확인한다.

**새 폴더는 캐시가 있어도 다시 내려받는다.** lock 파일(`.terraform.lock.hcl`)이 없는 새 폴더에서는 Terraform 1.4부터 캐시를 쓰지 않고 레지스트리에서 다시 받는다. lock 파일에 모든 OS용 체크섬을 적으려면 레지스트리에서 받아야 하기 때문이다. 받은 것은 캐시에 넣고 폴더에는 바로가기만 만들므로 **디스크에는 여전히 한 벌만** 남는다. 아끼는 것은 디스크이고, 새 폴더의 다운로드 시간은 아끼지 못한다. 2026-11-25에 작은 프로바이더(`hashicorp/null`)로 시험한 결과다.

| 폴더 상태 | `init` 출력 | 내려받음 | 폴더 안 |
|---|---|---|---|
| 새 폴더, 캐시 비어 있음 | `Installing` → `Installed ... (signed by HashiCorp)` | 예 | 바로가기 |
| 새 폴더, lock 파일 없음, 캐시에 있음 | `Installing` → `Installed ... (signed by HashiCorp)` | **예** | 바로가기 |
| lock 파일 있음 (`.terraform`만 지우고 다시, 또는 다른 폴더의 lock 파일을 복사) | `Using ... from the shared cache directory` | 아니오 | 바로가기 |

새 실습 폴더에서도 다운로드를 건너뛰고 싶으면, 같은 프로바이더를 쓰는 이전 실습 폴더의 `.terraform.lock.hcl`을 새 폴더에 복사한 뒤 `init`한다. lock 파일은 프로바이더 버전과 체크섬을 적은 파일이라 복사해도 된다. 대신 새 폴더도 같은 버전에 고정된다.

**캐시에 없을 때**

| 증상 | 흔한 원인 | 해결 |
|---|---|---|
| 2번에 아무것도 없고 4번에 `->`가 없다. 5번이 800MB쯤이다 | `.terraformrc`를 만들기 전에 `init`했다. 또는 파일 이름이나 경로에 오타가 있다 | 1번을 확인한 뒤, 실습 폴더의 `.terraform` 폴더만 지우고 `terraform init`을 다시 한다. `.terraform.lock.hcl`(버전 고정)과 `terraform.tfstate`(장부)는 지우지 않는다 |
| `find: '.../plugin-cache': No such file or directory` | 캐시 폴더를 만들지 않았다. Terraform은 캐시 폴더를 스스로 만들지 않는다 | `mkdir -p ~/.terraform.d/plugin-cache` 후 위와 같이 다시 `init` |
